# opx: agent instructions

opx takes the configs front-end developers copy into every project (linting, formatting, building, releasing) and puts them behind one lightweight, opinionated CLI that just works. You install the CLI and the plugins you want; opx finds what your repository needs, sets it up, and runs it. Every opinion can be swapped out.

## What good looks like

Weigh every change against these four goals.

1. **It just works.** Sensible defaults with no setup, settings only for real choices, and nothing to configure that opx can detect. A first run in a new repository should succeed without reading docs. When opx can't do something, it says why and what to do next.
2. **The CLI is professional.** Every command reads like a checklist: one status symbol per line, a short result, dim details, live progress for anything slow, and color that follows the terminal. It never dumps a stack trace unless asked (`--debug`). See [CLI output](#cli-output).
3. **Tests cover opx, not the tools it wraps.** Test what opx decides, builds, passes to a tool, and does with the result. Don't re-test ESLint rules, changesets, Node, or git. See [Testing](#testing).
4. **Plugins, like ESLint.** The CLI knows nothing about any specific tool. Each tool lives in a plugin package that implements one contract, is found by naming convention, and is loaded from the host's own `node_modules`. Anyone can publish one. See [Plugins](#plugins).

## Layout

| Path | Package | Role |
| --- | --- | --- |
| `opx/engine` | `@allons-y/opx` | The `Detector` contract, `.opx/config.json` and `.opx/state.json`, the plugin loader, package-manager detection, git hooks. No tool knowledge. |
| `opx/cli` | `@allons-y/opx-cli` | The `opx` binary: scans the tree, suggests plugins, and runs them. Commands live in `src/commands/`. |
| `opx/lint-js`, `lint-ts`, `lint-json`, `lint-md` | `@allons-y/opx-lint-*` | Lint plugins. Each ships an ESLint flat config as a plain array, so users can spread it into their own `eslint.config.js`. |
| `opx/release` | `@allons-y/opx-release` | The release plugin, built on changesets. |
| `opx/shared` | private | Source shared between plugins without a runtime dependency. `scripts/shared.js` copies it into each package when it's packed. |
| `opx/docs` | private | The docs site (Eleventy, with an API reference generated by TypeDoc). |
| `configs/` | | Shared build, lint, test, and TypeScript configs. |
| `scripts/` | | Repo scripts: shared-source copying, the smoke test, the Renovate changeset writer. |

The repo uses itself: `.opx/config.json` turns on the four lint plugins and the release plugin, and `yarn lint` is `opx lint`.

## Commands

| Command | What it does |
| --- | --- |
| `yarn build` | Build every package to its `bin/` folder (esbuild, then type declarations). |
| `yarn typecheck` | Type-check every package. |
| `yarn test` | Run the Jest suites. |
| `yarn coverage` | Tests with coverage. Each package must stay at or above 98% of lines and statements and 94% of branches and functions. |
| `yarn lint` / `yarn format` | Lint with opx, or lint and fix. |
| `yarn smoke` | Pack the packages, install them in a scratch project, and run the CLI. |
| `yarn docs:build` | Build the docs site. |
| `yarn changeset` | Record a change for the next release (`opx release add`). |

Run `yarn build` before `yarn test` or `yarn typecheck` in a fresh checkout: packages import each other's built output.

## Plugins

A plugin is a package whose default export is a `Detector` (`opx/engine/src/detector.ts`):

- **`id`, `shortName`, `displayName`:** the package id, the name used in config and commands (`js`), and the name people see.
- **`concern`:** `lint`, `build`, `release`, or `test`. Commands run every enabled plugin for their concern.
- **`detect(ctx)`:** whether the plugin applies, usually from `ctx.fileTypes`. Keep it fast and side-effect free.
- **`describe(ctx)`:** a summary and `bundledDeps`, the third-party packages the plugin ships.
- **`cleanup(ctx)`:** optional advice on what the project can drop once the plugin is on, such as a leftover `.eslintrc`. opx only ever deletes a suggested file that is empty and unchanged in git.
- **`run(ctx, args)`:** does the work.

Rules every plugin follows:

1. **Return an exit code; never call `process.exit`.** The host owns the one exit, so it can run several plugins and report the first failure.
2. **Write output through `ctx.write`, not `console`.** Hosts buffer and group output so parallel runs don't interleave.
3. **Ship your tools.** A plugin bundles the tools it runs as exact-version `dependencies`, and lists them in `bundledDeps`, so users install one package and get a working setup. A test checks the versions are pinned.
4. **Follow the naming convention.** `@allons-y/opx-<name>` for first-party plugins, `opx-plugin-<name>` or `@scope/opx-plugin-<name>` for everyone else. The loader skips anything else.
5. **Export configs users can compose.** A lint plugin's ESLint config is a plain array whose blocks are all scoped by `files`, so it mixes with other configs and with the user's own rules.

Config lives in `.opx/config.json`. Dynamic tasks (`lint`, `build`) map a plugin's short name to `true`, `false`, or its settings; read them with the engine's `enabledNames`. Static tasks (`release`, `test`) turn a whole task on or off. #58 lets them hold settings too, with an `isTaskEnabled` helper; once it lands, use that helper rather than comparing to `true`. The schema is `opx/engine/schema/config.json`.

Code two plugins share goes in `opx/shared` and is imported as `shared/<name>.js`; don't add a runtime dependency between plugins for it. A plugin can't import from the CLI.

## CLI output

The goal is a CLI that looks finished: calm, aligned, and clear about what happened and what to do next.

- **Every line has a status.** `✔` done, `–` skipped (dim, with why), `▲` warning, `✖` failed, `●` in progress. Indent two spaces; put details after the message, dimmed.
- **Say what's next.** After a failure, or when the user has to act, add a short hint line: the command to run or the setting to change.
- **Show live progress** for anything that takes more than a moment (installs, publishing, network calls), with a spinner or step lines, not silence.
- **Color follows the terminal.** `NO_COLOR` turns it off, `FORCE_COLOR` turns it on, otherwise only on a TTY. Fall back to ASCII symbols on the legacy Windows console.
- **Interactive only in a terminal.** Prompts use `@clack/prompts`. Without a TTY, or with `CI` or `OPX_NONINTERACTIVE` set, never prompt: use flags or fail with a message that names them.
- **No noise.** No stack traces without `--debug`, no `opx:` prefixes on styled lines, and problems go to stderr.
- **End long runs with a summary**, such as a table, when several packages or steps are involved.

The CLI's helpers are `opx/cli/src/colors.ts` and `@clack/prompts`. Plugins can't import the CLI, so #58 gives the release plugin its own small output helper (`opx/release/src/ui.ts`). When a second plugin needs one, move it into the engine so every plugin shares the same output.

## Testing

Tests are Jest with ts-jest, running as ESM (`configs/jest.config.js`), in `*.test.ts` files next to the source.

**Test opx's own behavior:** the decisions it makes, the config it builds, the arguments it passes to a tool, how it handles the tool's result and errors, and what the user sees. A test that would still pass if the opx code under it were deleted is not testing opx.

**Don't re-test the tools.** No tests that an ESLint rule fires, a fixer rewrites a file, changesets bumps a version, `JSON.parse` parses, or git behaves like git. Those projects test themselves. One smoke test per integration is enough: the shipped config loads, passes a clean file, and fails a bad one.

**Patterns:**

- **External tools:** mock `node:child_process` or pass an injectable dependency, then assert on what opx passes and how it handles the result. Code that touches the outside world takes its I/O as a parameter for this, such as `runAdd`'s `AddDeps` in `opx/release/src/add.ts`.
- **Git:** real git in a scratch repository is fine, and often clearer than a mock, when the test is about what opx does with git (tags, commits, hooks). Use `useScratch()` from `shared/testing.js`; it cleans up after each test. The Jest config already isolates tests from the machine's git config.
- **Network:** inject `fetch`. Tests never reach the network.
- **No order dependence.** Each test sets up its own state.
- **No tests that restate data,** such as a catalog's contents, or that repeat another test or the engine's own tests.

The audit in #51 applied these rules to the whole suite; follow its patterns.

## Code

- TypeScript, strict, `NodeNext` modules. Imports keep the `.js` extension; type-only imports use `import type`.
- Node 24 or later. Use built-ins (`fetch`, `process.loadEnvFile`, `fs.globSync`) before adding a dependency.
- Comments are short JSDoc. Explanations belong in the pull request or the docs.
- Formatting and style come from `yarn lint`; don't hand-format.
- Keep dependencies small. Every runtime dependency ships to every user.

## Docs

Change a command, flag, config key, or plugin behavior, and update its docs in the same pull request: the package `README.md` and its page under `opx/docs/src` (`cli/` for commands, `plugins/` for plugins). The API reference is generated from JSDoc on exported types, so keep those accurate.

## Releases and changesets

- Add a changeset (`yarn changeset`) for anything a user would notice. Tests, CI, docs, and internal refactors need none.
- Releases run through opx itself: `changesets/action` opens the release pull request, and merging it runs `yarn release` (`opx release publish`).
- The repo is in beta pre-release mode (`.changeset/pre.json`).

## Commits and pull requests

- [Conventional Commits](https://www.conventionalcommits.org), enforced by commitlint.
- One change per pull request. Fill in the sections of `.github/PULL_REQUEST_TEMPLATE.md`.
- When a pull request is ready for review, squash its commits into one, with the pull request's title as the commit message. A stacked pull request sits on its squashed parent.
- Pull request titles follow Conventional Commits too, including the release pull request, which `.github/workflows/release.yml` titles `chore(release): version packages`.
- CI must pass: lint, build, typecheck, tests on Node 24 and 26, Windows and macOS, coverage, the smoke test, and the docs build.
- The org-wide rules live in the [`.github` repository](https://github.com/allonsy-studio/.github/blob/main/docs/repository-standards.md); this file covers only what's specific to opx.

## Decisions

### The `version` script name

The root `version` script follows the org standards and runs as `yarn run version`. Plain `yarn version` is Yarn's own command, and `npm version` runs any script named `version` during its own bump.

We kept `version` for now. If the overlap causes trouble, rename the script to `version-packages`, the name the changesets docs use. Update the org standards, the root `package.json`, `.github/workflows/release.yml`, and the release docs in `opx/release/README.md` and `opx/docs/src/plugins/release.md` together.

### Changesets 2 and `workspace:` ranges

opx bundles `@changesets/cli` 2, which publishes with plain `npm publish` and leaves `workspace:` ranges as written ([changesets#432](https://github.com/changesets/changesets/issues/432)). The release docs tell users to use real semver ranges between their own packages because of it. When opx moves to Changesets 3, check whether the fix landed, then update the "Publishing a monorepo" sections in `opx/release/README.md` and `opx/docs/src/plugins/release.md`.
